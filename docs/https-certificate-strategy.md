# HTTPS and certificate strategy

## Goal

The Web UI must move from plaintext HTTP to authenticated TLS without weakening the existing session, CSRF or backup-security model.

The current Arduino `WebServer` implementation is intentionally not treated as an HTTPS-capable transport. The production HTTPS implementation will use Espressif's native HTTPS server component (`esp_https_server`) rather than an API-compatible third-party replacement that lacks header collection required by the current authentication flow.

## Transport policy

### Normal Wi-Fi client mode

Once HTTPS support is implemented:

- HTTPS on TCP 443 is the administrative endpoint.
- Plain HTTP on TCP 80 may exist only as a redirect to the HTTPS origin.
- Login, password changes, configuration writes, backup export/restore and authenticated APIs must never be served over plaintext HTTP.
- Session cookies use `Secure; HttpOnly; SameSite=Strict`.
- mDNS advertises `_https._tcp` on port 443.
- There is no automatic fallback from failed HTTPS to an authenticated HTTP session.

### Commissioning access-point mode

Commissioning has a different trust bootstrap problem because a new device does not yet possess a certificate trusted by the administrator's browser.

The first implementation may retain HTTP only for the isolated first-boot commissioning AP while all of the following remain true:

- the AP uses a random per-device WPA2/WPA3 credential shown locally on the display;
- the initial administrator credential is independently random and shown locally;
- commissioning HTTP is available only while the device is in AP commissioning mode;
- normal station-mode administration does not inherit this exception;
- the UI clearly identifies commissioning transport as local bootstrap rather than a trusted HTTPS session.

A future trusted commissioning mechanism may remove this exception.

## Certificate sources

The server certificate and private key are device-local security material and are not part of ordinary portable configuration backup.

Supported certificate sources are, in priority order:

1. **Administrator-provisioned certificate and private key**
   - PEM certificate chain and matching private key.
   - Intended for a private/internal CA or an environment where the device hostname is covered by a trusted certificate.
   - The firmware validates the certificate/key pair before activation.

2. **Device-generated self-signed certificate**
   - Fallback for HTTPS-capable deployments without a private CA.
   - The UI and display expose a SHA-256 certificate fingerprint for out-of-band verification.
   - A self-signed certificate provides encryption but does not become browser-trusted merely because it was generated by the device.

Public-CA issuance is not the default strategy because local mDNS names and offline/isolated deployments cannot reliably depend on public ACME issuance.

## Private-key handling

- Private keys are never returned through status, diagnostics or backup APIs.
- Private keys must not be logged.
- Certificate replacement requires an authenticated, CSRF-protected administrative action.
- The active certificate/key pair is replaced only after the new pair has been parsed and validated.
- Factory reset removes user-managed certificate/key material.
- Flash encryption / NVS encryption is a separate platform-hardening concern and must not be implied merely by storing the key in NVS.

## Certificate lifecycle

The UI should expose:

- certificate source: provisioned / self-signed;
- subject and issuer;
- validity window;
- SHA-256 fingerprint;
- active hostname/SAN coverage where available.

Replacement flow:

```text
upload certificate + key
 -> parse
 -> verify key matches certificate
 -> validate supported key/certificate format
 -> stage
 -> atomically activate
 -> restart HTTPS service if required
```

An invalid replacement leaves the currently active certificate untouched.

## Session and browser policy

When HTTPS is active:

- session cookie: `Secure; HttpOnly; SameSite=Strict; Path=/`;
- existing inactivity and absolute session lifetimes remain unchanged;
- existing CSRF protection remains mandatory;
- sensitive responses continue to use `Cache-Control: no-store`;
- security headers should include at least `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a restrictive Content Security Policy suitable for the inline UI;
- HSTS is enabled only where the administrator has a certificate path that browsers can validate consistently. It must not make self-signed recovery or commissioning impossible.

## Implementation direction

Use Espressif's native `esp_https_server` / HTTP server stack. This keeps TLS on the vendor-supported ESP-IDF path and allows explicit handling of request headers, sessions and TLS configuration.

The migration should be staged:

1. enforce the host-tested `WebTransportPolicy` contract for commissioning HTTP, legacy station HTTP redirects and station HTTPS;
2. separate Web UI request/business logic from the Arduino `WebServer` transport;
3. add an ESP-IDF HTTP/HTTPS adapter with equivalent request-header access;
4. preserve all current authentication, CSRF, login-throttle, backup and event semantics;
5. add certificate-store validation and atomic certificate activation;
6. enable HTTPS for station mode and mark cookies `Secure`;
7. retain only the explicitly scoped commissioning-AP HTTP exception;
8. add target-device integration tests for TLS handshake, certificate replacement and session behavior.

Do not run two independent administration implementations with divergent authorization logic. The transport adapter must feed the same Web-service behavior.

## Validation still required

Software implementation is not complete until target-device testing covers:

- TLS handshake success and failure paths;
- heap usage and connection limits under HTTPS;
- certificate/key parsing and replacement;
- browser behavior with provisioned trusted certificates;
- self-signed fingerprint verification workflow;
- HTTP-to-HTTPS redirect behavior in station mode;
- commissioning-AP exception boundaries;
- session cookie `Secure` behavior;
- reboot/power-loss during certificate replacement.

### Transport-policy contract

`include/core/WebTransportPolicy.h` captures the intended transition without depending on Arduino networking classes. It defines that authenticated administration is permitted for commissioning HTTP and station HTTPS, while legacy station HTTP is redirect-only. It also defines the expected administration port, mDNS service and Secure-cookie requirement for each mode. The policy is host-tested and must be consumed by the eventual transport adapter rather than duplicated there.
